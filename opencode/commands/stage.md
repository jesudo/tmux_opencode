Stage the changes relevant to the current conversation in the current Git repository. Additional user direction: $ARGUMENTS

**Hard pre-approval gate:** Until the mandatory question in step 6 has returned an explicit answer, do not run any Git command that changes the index, working tree, history, branch, remote, or tags. In particular, do not run `git add`, `git commit`, `git restore --staged`, `git reset`, `git rm`, `git mv`, `git checkout`, `git switch`, `git rebase`, `git merge`, `git cherry-pick`, `git push`, or an equivalent command. Reading status and diffs is allowed. The default is **Do nothing**: if the question is unavailable, fails, is dismissed, returns an unrecognized answer, or does not explicitly select an action, make no Git changes and stop.

1. Inspect `git status --short`, `git diff`, and `git diff --cached`. Do not alter already staged changes unless they are part of the current request.
2. Identify only files that were created, changed, or explicitly requested during this conversation. Do not stage unrelated files.
3. Inspect every selected path and its diff for material that should not be tracked. Never stage credentials, passwords, API keys, tokens, private keys, certificates, `.env` files (except intentionally safe examples such as `.env.example`), credential stores, or configuration containing real secret values. Treat secret-like filenames (for example `*.pem`, `*.key`, `id_rsa`, `credentials*`) and values (for example bearer tokens, private-key blocks, connection strings with passwords) as suspicious. Leave suspicious files unstaged and clearly warn the user; do not rely solely on `.gitignore`.
4. If no safe files are selected, report that no files are proposed for staging and stop. Otherwise, before making any Git changes, send a user-visible proposal containing the exact files proposed for staging, files deliberately excluded, every warning raised, and two commit messages based only on the proposed selected diff: a concise imperative Conventional Commit-style subject of 72 characters or fewer and an extended multi-line message with that subject followed by a blank line and a short explanatory body when it materially clarifies the change. Label them `Proposed commit message:` and `Proposed extended commit message:`.
5. If the index already contains changes not attributable to this conversation, warn that either commit option will commit the complete staged index. Include this warning in the visible proposal before asking the question.
6. **Mandatory single decision gate:** immediately set `@opencode_stage_waiting` to `1` on `$TMUX_PANE` with `tmux set-option -p -t "$TMUX_PANE" @opencode_stage_waiting 1` when running inside tmux (silently continue if tmux is unavailable). Then immediately call the question tool. Ask “What should I do with the proposed changes?” with header `Stage changes` and these options in this order:
    - **Do nothing (recommended):** make no Git changes and stop.
    - **Stage only:** stage only the exact paths in the visible proposal.
    - **Stage and commit with concise message:** stage the exact proposed paths, then commit the complete staged diff with the displayed `Proposed commit message`.
    - **Stage and commit with extended message:** stage the exact proposed paths, then commit the complete staged diff with the displayed `Proposed extended commit message`, preserving its line breaks.
7. As soon as the question tool returns, clear `@opencode_stage_waiting` with `tmux set-option -p -t "$TMUX_PANE" @opencode_stage_waiting 0` when running inside tmux (silently continue if tmux is unavailable), before doing any Git action. If the question tool is unavailable or fails, clear the flag, clearly report that the choice could not be shown, and leave everything unchanged. If the user selects **Do nothing**, dismisses the question, or gives any answer other than the three explicit action options, make no Git changes and stop. Do not stage anything unless the user explicitly selects an action option.
8. After the selected action is known, recheck every selected path and its diff for sensitive material, then stage only the approved files with `git add -- <explicit paths>`. Never use `git add .`, `git add -A`, or a broad pathspec.
9. Reinspect the full staged diff for sensitive material after staging. If anything suspicious is found, immediately unstage only the affected explicit paths with `git restore --staged -- <explicit paths>`, report the warning, and do not commit.
10. If a selected file contains changes that may not belong to this conversation, stage the full file anyway, then clearly warn that the file may include unrelated changes.
11. If staging more than 10 files or more than 500 added and deleted lines in total, clearly warn that the staged change set is unusually large. Continue with the selected action unless the user has said not to.
12. Run `git diff --cached --check` after staging. If it fails, report the problem and do not commit.
13. If **Stage only** was selected, report the files staged by this command, files deliberately left unstaged, and every warning raised, then stop.
14. For a commit option, commit only after successful completion of steps 8 through 12. Do not commit unless the user explicitly selected that action in the single decision gate. Never push from this command.
